# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OcelotJS is Julien Olivier's fork of Fabrice Bellard/quickjs-ng's QuickJS JavaScript engine
(`origin` is `github.com/j-olivier/Ocelot-JS`). The current branch (`dev_pal`) is, at present,
byte-for-byte identical to `master` (plain upstream quickjs-ng) — no fork-specific changes have
landed here yet.

There is a separate `dev` branch with a substantial, though possibly abandoned/superseded, first
attempt at the fork's actual goal: decoupling the engine core (`quickjs.c`) from the host C
runtime/OS by routing every OS-dependent primitive (malloc/free/realloc, abort, time/timezone,
mutexes, condition variables, atomics) through an injectable **PAL** (Platform Abstraction Layer)
struct passed into `JS_NewRuntime2()`, plus a parallel Visual Studio build. That branch also
introduces `quickjs-pal-def.c/h` (default PAL impl), `quickjs-dump.c/h` (split out `FILE*`/printf-based
dump routines so the core doesn't need `<stdio.h>`), an `andjs/` sample host, and `OcelotJS.sln`/
`OcelotJS.vcxproj`. Given the `dev_pal` branch name, that work is likely being redone/continued
here — `git log dev` and `git diff master...dev` are the best reference for the intended shape of
the PAL boundary before re-implementing it.

## Environment note

This repo builds via MSYS2 mingw64. MSYS2 is installed at `F:\msys64` but is **not** on `PATH`
inside the Bash tool's shell by default (`make`/`gcc`/`cc` don't resolve there). Prefix build
commands with that toolchain's bin dirs, e.g.:

```
PATH="/f/msys64/mingw64/bin:/f/msys64/usr/bin:$PATH" make -j$(nproc)
```

(`/f/msys64/mingw64/bin` has `gcc`; `/f/msys64/usr/bin` has `make`.) Don't assume a bare `make`/
`gcc` invocation works without this — verify or prepend the PATH first rather than guessing.

## Build commands (Unix/make — Linux, macOS, BSD, MinGW, Cosmopolitan)

- `make -j$(nproc)` — build `qjs`, `qjsc`, `run-test262`, and `libquickjs.a`. Add `CONFIG_WERROR=y`
  to treat warnings as errors (this is what CI does).
- `make test` — run the built-in JS test suite (`tests/test_*.js`, executed via `qjs`).
- `make microbench` — run `tests/microbench.js` and report timing.
- `make test2-bootstrap` — clone/pin the test262 checkout (commit/date controlled by
  `TEST262_COMMIT`/`TEST262_SINCE` at the top of the Makefile) and apply `tests/test262.patch`.
- `make test2` — run the full test262 suite (both strict and non-strict) against `test262.conf`,
  comparing against the known-failures list in `test262_errors.txt`. `make test2-default` runs it
  once (non-strict only); `make test2o`/`test262o.conf`/`test262o_errors.txt` is the legacy ES5
  suite. Append `-update` (e.g. `make test2-update`) to regenerate the expected-errors file after a
  legitimate behavior change.
- `make testall` — build + `test` + `microbench` + `test2o` + `test2`.
- Config flags, passed as `make VAR=y ...`: `CONFIG_WIN32` (MinGW cross build; auto-detected under
  MSYS2), `CONFIG_M32` (force 32-bit), `CONFIG_LTO`, `CONFIG_ASAN`/`CONFIG_MSAN`/`CONFIG_UBSAN`/
  `CONFIG_TSAN`, `CONFIG_COSMO` (Cosmopolitan build), `CONFIG_CLANG`, `CONFIG_PROFILE`.
- Single test262 test: build `run-test262`, then run it directly — `./run-test262 -f <path>` for one
  file, or see the full flag list at the top of `run-test262.c` (`usage()`, ~line 2218): `-c` config
  file, `-d` directory tree, `-a` strict+nostrict, `-t` timings, `-u` update errors, `-T N` thread
  count, `-E` only re-run known failures.
- CI (`.github/workflows/ci.yml`) is the source of truth for "passing": Linux (+LTO, 32-bit,
  ASan/MSan/UBSan), macOS (+ASan/UBSan), FreeBSD, Cosmopolitan, MinGW-on-Wine, Windows/MSYS2, and a
  QEMU-emulated matrix (386/riscv64/arm64/arm/s390x/ppc64le) all build and run at least `make test`.

## Architecture

- `quickjs.c`/`quickjs.h` — the engine proper: lexer/parser, bytecode compiler, interpreter, and
  every built-in object (numbers, strings, `Array`, `Map`/`Set`, `Proxy`, `BigInt`, async/
  generators, modules, etc). This is the file almost all engine-level changes touch.
  `quickjs-atom.h` holds the built-in atom table; `quickjs-opcode.h` the bytecode opcode list —
  both are consumed via `#include` + X-macro patterns inside `quickjs.c`, so adding an opcode or
  atom means editing these headers *and* the corresponding switch/table in `quickjs.c`.
- `libregexp.c`/`.h` (+ `libregexp-opcode.h`) — a standalone regexp engine (its own bytecode VM)
  used by `quickjs.c` but independently testable (`make regexp_test`).
- `libunicode.c`/`.h` (+ generated `libunicode-table.h`) — Unicode property/case-folding tables.
  `libunicode-table.h` is generated by `unicode_gen.c` from `unicode/UnicodeData.txt` (fetched via
  `unicode_download.sh`); only regenerate it if you've actually changed Unicode data handling.
- `dtoa.c`/`.h` — float64 <-> decimal string conversion (Grisu/Ryu-style), used for `Number`
  formatting and parsing.
- `cutils.c`/`.h`, `list.h` — shared low-level helpers: dynamic buffers (`DynBuf`), intrusive
  doubly-linked lists, bit tricks. No JS semantics live here.
- `qjs.c` (REPL/CLI) and `qjsc.c` (bytecode compiler CLI) are separate executables that both link
  `quickjs-libc.c`/`.h` — the `std`/`os` JS modules (file I/O, `os.Worker` threads via POSIX
  pthreads, timers, signals, `poll()`-based I/O). This libc layer is a *host binding* layer, kept
  deliberately separate from the core engine so the core doesn't hard-depend on stdio/POSIX.
  `repl.c` is generated from `repl.js` by `qjsc` (`make` regenerates it; don't hand-edit `repl.c`).
- `run-test262.c` — the test262 conformance harness: multi-threaded runner, config-driven
  (`test262.conf`/`test262o.conf`), diffed against the known-failure allowlists
  (`test262_errors.txt`/`test262o_errors.txt`).
- `examples/` — small standalone-compilation demos (`qjsc -e` embedding a script as C, loadable
  native modules via `.so`); `fuzz/` — libFuzzer targets (bytecode, compile, eval, JSON, regexp),
  built independently of the main `make all` targets; `tests/` — the JS-level suite above plus
  native test helpers (e.g. `tests/bjson.c`, a binary-JSON module loaded at test time).
- `doc/quickjs.texi` is the canonical API reference source; `make build_doc` renders it to
  `doc/quickjs.pdf`/`doc/quickjs.html`.

### Working against upstream

This is a fork that intends to keep tracking upstream quickjs-ng. When touching `quickjs.c`,
prefer minimal, surgical diffs over reformatting/reordering — the `dev` branch's own commit history
(e.g. "reorder file content to fit original quickjs order and reduce changes for future git sync")
shows this project explicitly optimizing for mergeability with upstream. Keep that in mind before
introducing large structural changes to files shared with upstream (`quickjs.c`, `quickjs.h`,
`cutils.h`, `dtoa.c`, `libregexp.h`), and prefer isolating fork-specific code in new files (as the
`dev` branch does with `quickjs-pal-def.c`, `quickjs-dump.c`) over interleaving it into upstream
files.
